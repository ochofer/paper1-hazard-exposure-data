PROVENANCE RERUN AND DETERMINISM FIX, 7 September 2026

WHY. Scripts 04, 06 and 07 were rerun UNCHANGED against the pinned V1 files
solely to emit RUN_PROVENANCE records. Their outputs on disk were written on
23 August 2026, before the provenance code existed, so gate 5 of the ruling of
6 September could not be met for any figure resting on them. The design chat
instructed on 7 September that the rerun be written beside the 23 August
outputs, never over them, diffed digit for digit, and the comparison recorded.

DIAGNOSIS. Order, not content. Both differing files had the same row count, the
same header, and an identical SHA-256 once sorted. No value in either file
changed and no reported figure moved: every summary output, including
R = 36.0%, was byte-identical.

  The cause is the trap already recorded in this project. Both files are built
  by iterating Python sets, and string hashing is randomised per process, so
  the row order varies between runs while the content does not.

FIX, in code rather than in a note. Both scripts now sort before writing:
  06_change_decomposition.py   sort_values([bucket, subject, party], mergesort)
  04_vintage_diff.py           sort_values(all columns, mergesort)

CONCLUSION. No figure in the note is affected. The 23 August summary outputs
stand as the figures of record. The two row-level CSVs are now byte-reproducible,
which they were not before, so a checksum on them is finally worth recording.
This was a self-inflicted instance of the note's own subject: an output whose
fingerprint moved between runs while its content did not.
