C. Panel A, the Fama-French factors

C1. Run the download and parse cell YOU

Pulls F-F_Research_Data_Factors_daily_CSV.zip from Ken French's library and parses it. Expect a full range starting 1926-07-01 and roughly 25,000 rows before clipping.

This parser is the one piece already tested. It was run against synthetic files reproducing the real format quirks: the copyright preamble, the trailing copyright line, the missing value codes, and the annual block that monthly files append after the monthly rows.

That testing found two genuine bugs, both now fixed. Using pd.NA was silently converting the factor columns to object type, which would have broken the summary table and the magnitude check further down. And malformed input raised a bare StopIteration instead of a readable error.

If it fails

ValueError: No YYYYMMDD rows found. The URL is pointing at a monthly file. Monthly dates are six digits and need a different parser plus handling for the annual block. Check the filename contains _daily.

HTTP 404. French occasionally renames files. Open the data library page and copy the current "Fama/French 3 Factors [Daily]" CSV link.

Timeout or connection error. The Dartmouth server is genuinely slow at times. Just run the cell again; nothing is cached, so a retry is clean.

C2. Sanity check the summary table YOU

The window is fixed at 2010-01-01 to 2025-12-31, set in advance so that a rerun on a different day produces an identical file rather than a quietly longer one. Expect roughly 4,000 rows.

The values are in percent, not decimals. Mkt-RF = 0.55 means 0.55 percent. They are stored exactly as published, deliberately, because the division by 100 belongs in the analysis layer where it can be seen in a diff.

Daily Mkt-RF should sit mostly between minus 3 and plus 3, with a standard deviation near 1. If the standard deviation is near 0.01, something has already divided by 100 and everything downstream will be wrong by two orders of magnitude.

F2. Run section 2b, then Panel B YOU

Do not run Panel B before section 2b. Your interrupted run on 21 August is why. It was downloading ALIZY, ALIZF, AKZOY, AKZOF, ADMUSD and hundreds more. Those are American depositary receipts, US foreign-board lines and currency-denominated order-book lines of companies you already had. ALV, ALIZY and ALIZF are all Allianz.

Three problems, and the first is the one that matters. The panel would double count: a hazard-sorted portfolio holding all three Allianz lines holds one bet with three weights, and because the duplicates are near perfectly correlated they look like independent observations, so your cross-sectional standard errors come out too small. A receipt is not the security: an ADR carries the underlying return plus an exchange rate move, traded on US hours against a European close, which injects a currency factor into a climate-hazard sort. And it costs a multiple of the download time while the subscription is running.

Section 2b fixes it by letting liquidity arbitrate rather than by hand-maintaining a table of exchange codes. For every candidate it asks FMP what it can price, pulls one recent quarter, and keeps the line with the highest median daily dollar volume. Median rather than mean, so a single index-rebalance day cannot decide a listing; dollar rather than share volume, because share counts are not comparable between a euro ordinary and a dollar receipt.

Simplest path: push, reopen the notebook from GitHub, then Runtime, Run all. Every section now runs in dependency order and the slow parts are cached, so a rerun costs minutes rather than repeating the whole job. Expect roughly fifteen minutes end to end, most of it the Panel B fetch.

G. The remaining tests

These are the things that stand between a working download and a defensible result. None is blocked by anything except the data pull, and the first two decide whether the paper's central estimate can be trusted at all.

G1. Blocking test 1, the survivorship hit rate BLOCKED

Blocked on the paid key, and it is the first thing to run once you have one. code/01_survivorship_test_fmp.py exists but has never returned a number, and it still points at the retired /api/v3/ paths, so it needs the same URL fix the notebook got before it will run at all.

The question it answers: of the firms that owned assets in the GEM file at the start of the sample, what fraction had left the listed universe by the end, and how do their returns compare with the survivors. Until that fraction is a number, survivorship bias in this paper is of unknown size, which is not the same as small. Commit to how you will handle it before you see the figure, so the threshold cannot move to accommodate the result.

G2. Audit the delisted list before trusting the rate BLOCKED

New, and it comes out of the 2c run. The free-tier sample of delisted names included EQR, which is an active S&P 500 REIT. One observation is not a verdict, but it is enough to require a check, because blocking test 1 divides by the size of this list.

The direction of the error matters more than its size. A list inflated with still-listed firms makes the delisting rate look higher, which sounds conservative. But used the other way, as a denominator, an inflated list makes the fraction of your own universe that delisted look smaller, and an understated survivorship rate is exactly the error that makes a bias look safe to ignore. Take a sample of fifty names off the list, check their current listing status against the profile endpoint, and report the false positive rate in the methods section.

G3. Factor replication, 02_factor_replication.py UNTESTED

Also still on /api/v3/ and also never run. Its job is to confirm that returns computed from your own price panel reproduce known factor behaviour before that panel is used to estimate anything new. Standard order of operations: reproduce something known, then measure something unknown.

Concretely: regress a handful of your own daily return series on the Ken French factors and check the betas land where published estimates put them. If a large-cap energy name does not come back with a market beta near one, the problem is in the return construction, and finding that here costs an afternoon rather than a chapter.

G4. The GEM vintage problem, still the critical path BLOCKED

Unchanged since the 19 August handover and still the most serious problem in the project. The GEM ownership snapshot is undated, with sector trackers published across a span of roughly sixteen months. Using a 2026 ownership snapshot to explain 2010 returns attributes to a firm assets it did not own yet.

This one contaminates the regressor, which is why it outranks everything else here. Survivorship bias distorts the dependent variable and can be bounded and reported. Look-ahead in the independent variable means the exposure measure is partly constructed from information that did not exist at the time, and no amount of care downstream repairs that.

The unblocking path is already in motion: Gabe at GEM is sending prior dataset releases plus a version carrying a last-verified-date column. When that arrives, the exposure measure gets rebuilt as a time-varying panel using only vintages available at each date. Two things to hold on to when you reply to him: a last-verified date bounds knowledge rather than dating events, so an asset verified in 2024 may have changed hands in 2019 and simply not been rechecked; and ask explicitly whether the prior releases are archived as originally published or restated, because a restated archive reintroduces the same look-ahead in a form that is much harder to notice.
